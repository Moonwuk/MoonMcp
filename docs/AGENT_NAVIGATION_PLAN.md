# План оптимизации MoonMCP и навигации агента

Первоначальная основа: main после PR #4, merge-коммит `7f29967`. Статус обновлён 14 октября 2026 года для версии с флагами и управляемым исполнением. Практический маршрут и контракты API: [памятка агенту](AGENT_WORKFLOW.md). Ниже сохранены критерии развития; их наличие не означает, что все этапы и исследования закончены.

## Цель

Агент должен выбирать следующий полезный шаг по цели, наблюдениям и оставшемуся бюджету, получать небольшой релевантный набор инструментов и продолжать работу после перезапуска без повторного обследования. Сокращение вызовов не должно ухудшать покрытие или качество подтверждения результатов.

## Текущий статус реализации

| Направление | Реализовано | Что остаётся проверить или расширить |
| --- | --- | --- |
| Выбор инструментов | `ToolSpec`, живые схемы и gate-маркеры; Unicode/snake_case, BM25, предметные aliases; `tool_search`, `tool_describe`, причины доступности | Независимый retrieval-набор, более широкий языковой словарь; каталог и профили ещё используют явные списки |
| Компактное представление | Compact с fallback, summary/full, полные chunks с SHA-256; stdio-замер начальных схем −92,99% | Проверки других MCP-клиентов и качества агента; автоматическая подгрузка схем host не гарантируется |
| Бюджеты и исходы | `run_execute`, запись вызова до действия, учёт отправок общего HTTP-клиента, явные ошибки и неизвестные исходы | Raw DNS/TLS, браузер, CLI и непроверенные составные инструменты исключены из managed execution; прямые typed-вызовы не охвачены бюджетом run |
| Восстановление | Постоянные findings и IDs, `run_brief`, claim/heartbeat; `run_recover` и `run_reconcile` с доказательствами, затем явный retry | Lease не обеспечивает exactly-once внешних действий; исходный `unknown` сохраняется рядом с отдельным resolution; auth проверяется отдельно |
| Накопительный анализ | Флаги, evidence/source groups, контекст роли и времени, связи, противоречия, гипотезы и история пересмотра | Качество итоговых выводов агента нужно измерять на размеченных сценариях; автоматического подтверждения уязвимости нет |
| Проверки | Локальные сценарии и тесты контрактов, profile/gates, retrieval, зависимостей, памяти, восстановления и бюджетов | Нет независимой оценки экономии токенов или качества модели; историческая цель −30% пока остаётся целью |

На 11 диагностических запросах известных проблем ожидаемый инструмент попадал в top-5 в 2 случаях у прежнего алгоритма и в 11 у нового. Это development-набор, а не held-out benchmark. Полные результаты проверки конкретного изменения следует читать в его PR/CI.

Исследования и границы выводов: [аудит инструментов из PR #11](https://github.com/Moonwuk/MoonMcp/blob/de198f89bf790be5b5deec6cb1eae2a00f998bf9/docs/AGENT_TOOLING_RESEARCH.md), [похожие реализации флагов](FLAG_SYSTEM_RESEARCH.md).

## Что уже есть и где ограничения

- `tool_catalog(family=...)` группирует инструменты; для выбора следующего действия использовать короткую выдачу `tool_search`, затем `tool_describe`.
- `MOONMCP_PROFILE`, `MOONMCP_EXPOSE_TOOLS`, `MOONMCP_HIDE_TOOLS` фильтруют инструменты при старте. Неизвестный профиль оставляет ограниченный набор ориентации (fail closed). Compact уменьшает рекламируемый набор, сохраняя ограничения логического профиля; без `run_start`/`run_execute`, как в профиле `knowledge`, остаются прямые tools.
- Семейства служат навигацией, но не заменяют признаки риска отдельного инструмента. Например, семейство `orchestration` содержит и локальные `run_*`, и сетевые `recon_target`/`probe_batch`.
- `run_*` сохраняет задачи, покрытие, артефакты и счётчики при настроенном `MOONMCP_STATE_DIR`. Автоматический учёт относится к поддерживаемым вызовам через `run_execute`; ручной `run_usage` не делает остальные прямые вызовы управляемыми.
- `FindingsStore` использует SQLite при постоянном state dir, сохраняя идентификаторы. Отдельный реестр флагов хранит исходные наблюдения и историю гипотез; совпадения памяти не повышают доверие автоматически.

## Навигация, доступная агенту уже сейчас

1. **Ориентация:** `server_status` → `scope_list`; каталог читать по нужному семейству и кэшировать на сессию. При смене конфигурации обновлять кэш.
2. **Восстановление:** `run_list`/`run_brief` → `analysis_brief(project, target, run_id)` и `memory_brief(target)`. Проверять применимость старых наблюдений: target, scope, auth-роль и свежесть.
3. **План:** существующий run продолжать; для нового использовать `run_start`. Каждая задача содержит гипотезу, минимальное действие, критерий завершения и лимит работы.
4. **Выбор:** `run_next`/`run_claim` → `tool_search` → `tool_describe`. Не запускать повторно составляющие `recon_target`, если их актуальные результаты уже получены.
5. **Выполнение:** вызвать поддерживаемый инструмент через `run_execute`, проверить исход и счётчики, сохранить артефакт и флаг, обновить покрытие и задачу. Lease поддерживать heartbeat. Прерванный `running` после остановки run и истечения lease переводить через `run_recover` в `unknown`; разрешать неизвестный исход через `run_reconcile` с артефактами до повторения.
6. **Развилка:** связать флаги с проверяемой гипотезой и альтернативами; при наличии lead перейти к контрольной проверке. При отказе бюджета остановить работу; при отсутствии предпосылки отметить блокировку с причиной. Ошибка проверки не означает опровержение гипотезы.
7. **Завершение:** подтвердить результаты, выполнить triage/export, сохранить экспорт артефактом и вызвать `run_finish`. Успешное завершение run не означает отсутствие уязвимостей; отдельно перечислять пропущенные и заблокированные проверки.

| Наблюдение или цель | Следующий минимальный набор |
| --- | --- |
| Неизвестная поверхность | `http_probe`/`fingerprint`; затем только необходимые составляющие разведки |
| OpenAPI или JS-эндпоинты | `parse_openapi` / `analyze_js`; затем уточнение параметров |
| Авторизация и роли | `auth_set`, `access_control_check` / `authz_probe` при наличии нужного контекста |
| Признаки GraphQL | `graphql_check`; углубление по конкретному наблюдению |
| JS-приложение, данные не видны в HTML | `browser_open`; дальнейшие действия по DOM/сетевым наблюдениям |
| Неоднозначное поведение параметра | справочник класса → подходящий детектор; подтверждение отдельно |
| Lead | специализированная проверка, baseline и контроль → `confirm_finding`/`promote_lead` по применимости |
| Готовые результаты | `triage_findings` → export → артефакт → `run_finish` |

Профиль и семейство не являются разрешением на действие: агент проверяет scope, доступность, auth и фактические признаки intrusive конкретного инструмента.

## Этапы и оставшиеся критерии

### Этап 0. Измеримый baseline и короткая памятка

**Статус:** локальные сценарии и [памятка](AGENT_WORKFLOW.md) существуют. Их проверка не заменяет полноценную оценку агента на независимых задачах.

Создать набор локальных сценариев: новый target, продолжение run, GraphQL, авторизованный сценарий, ложный lead, отсутствие браузера и исчерпанный бюджет. Зафиксировать число вызовов, объём схем и результатов, запросы к fixture, длительность, покрытие и качество выводов. Свести операторскую инструкцию к маршруту выше; подробные справочники подключать по задаче.

**Готово, когда:** сценарии воспроизводятся, стоимость измеряется, одинаковая работа распознаётся как повторная. Не использовать число вызовов как единственный показатель качества.

### Этап 1. Единый реестр и выбор инструментов по задаче

**Статус:** поиск, ToolSpec и описание схем реализованы. Расширение профилей под роли и генерация всех навигационных данных из одного источника остаются отдельными задачами.

Развивать `ToolSpec`: уточнять типы I/O, примеры использования и проверенные оценки стоимости там, где они доступны. Свести оставшиеся списки каталога и профилей к единому источнику, сохраняя сверку с реальными gate-маркерами.

Использовать реализованный `tool_search(query, phase, available_only, limit)` с короткими карточками и причинами выбора. Выдача по умолчанию содержит до пяти инструментов. Неизвестный профиль сохраняет fail-closed поведение с ограниченной ориентацией.

Разделить локальную координацию и сетевые composite-инструменты. Создать профили coordinator/mapper/validator/reporter и проверить, что каждому доступны необходимые memory/run API.

**Готово, когда:** каждый инструмент имеет контракт, нет скрытых изменений риска, типовые сценарии находят релевантные кандидаты в первых пяти результатах.

**Ограничение:** короткий каталог сам по себе не уменьшает объём всех MCP-схем в контексте клиента. Начать со статических профилей; динамическую подгрузку реализовать в host/client с соответствующей поддержкой. Не обещать её за счёт одного нового инструмента поиска.

### Этап 2. Компактные результаты и устранение повторов

**Статус:** summary/full, полное сохранение большого вывода в chunks с SHA-256 manifest, чтение артефактов частями и ограниченный кэш встроенных справочников реализованы. Обрезается только preview. Произвольные сетевые ответы не кэшируются; единый новый формат всех старых tools не введён.

Развивать режимы summary/full, пагинацию и получение артефакта по идентификатору. Для результатов, где это применимо, сводить наблюдения, verdict, ограничения, ссылки на доказательства и несколько возможных следующих действий; большие тела хранить отдельно. Сохранять существующий формат для текущих клиентов либо выпускать версионированный контракт.

Идентифицировать проверку по run, нормализованному target, инструменту, параметрам, auth-контексту и версии. Кэшировать только подходящие операции; задавать TTL и инвалидировать при изменении auth, scope или target. Проверки с побочными эффектами не считать автоматически безопасными для повторного исполнения или кэширования. Следующие действия выдавать как предложения, не запускать их автоматически.

**Готово, когда:** неизменённые безопасные проверки используют свежий результат; клиент может получить полное доказательство; смена роли не возвращает результат другого пользователя.

### Этап 3. Автоматическое исполнение в контексте run

**Статус:** реализован для проверенного набора локальных и HTTP-инструментов через `run_execute`. Browser/CLI/raw transports пока отклоняются этим исполнителем; оценки не выдаются за точные измерения.

Сохранять связь вызова с `run_id`/`task_id`, резервирование до выполнения и проверку лимитов перед каждой HTTP-отправкой. Для расширения на browser/external CLI сначала разработать и проверить собственный учёт транспорта; явно различать измеренные и оценочные затраты.

Pause/cancel и исчерпание бюджета должны прекращать выдачу новой работы и сетевые операции в точках, где отмена поддерживается. В журнале сохранять частичные результаты. Усилить state machine: переходы задач, проверки зависимостей и явная политика завершения для failed/cancelled/blocked с сохранением причин.

**Готово, когда:** пропущенный ручной `run_usage` не позволяет превысить лимит; конкурирующие подключения не теряют счётчики и не удерживают блокировку после отказа; остановленные задачи не начинают новые запросы.

### Этап 4. Полное восстановление и несколько исполнителей

**Статус:** persistent findings, `run_brief`, claim, heartbeat, `run_recover`, `run_reconcile` и явный retry реализованы. Истёкший lease переводит работу в блокировку для сверки. Recovery требует остановленного run и отсутствия живого lease; reconcile добавляет решение с evidence-артефактами, сохраняя исходную `unknown` запись.

Сохранять findings с привязкой к run и артефактам, стабильными ID и источником. Развивать `run_brief` как сводку цели, задач, покрытия, бюджета, ограничений и релевантных результатов. Scope и auth после перезапуска проверять отдельно, не помещать секреты в резюме.

Для нескольких workers использовать атомарный claim задачи, lease и heartbeat. Просроченную задачу возвращать в очередь только через явный retry после сверки доказательств; неразрешённые running/unknown invocations блокируют retry. Результат reconcile не повторяет действие и не стирает историю. Независимые чтения выполнять параллельно; работу с одной сессией и изменяющие состояние действия сериализовать.

**Готово, когда:** новый процесс продолжает run с прежними findings и доказательствами; два workers не получают одну задачу; устаревший auth-контекст обнаруживается до сетевого вызова.

### Этап 5. Оценка качества и закрепление

**Статус:** регрессионные проверки добавлены; критерии экономии контекста и качества расследования не считаются достигнутыми без соответствующих измерений.

Сравнить с baseline на тех же fixtures. Стартовая цель — сократить объём контекста и повторные безопасные вызовы на 30% без падения покрытия и качества подтверждения; это целевой показатель, не обещанный результат. Уточнить его после измерений.

В CI проверять соответствие реестра и gates, доступность инструментов в профилях, корректность поиска, совместимость ответов, конкурентный учет, восстановление и политику завершения. Использовать семантические проверки маршрутов и результатов; не привязывать тесты к одному точному порядку всех вызовов.

## Зависимости дальнейшего развития

1. Независимый набор оценки поиска и расследований, включая отрицательные случаи и стоимость доказательств.
2. Поддержка дополнительных транспортов после проверки точного учёта и остановки.
3. Интеграции compact/dynamic loading с конкретными клиентами и измерение полного workflow.
4. Проверка масштабирования памяти, связей флагов и длинных расследований.
5. Ограниченный автономный цикл после проверки качества вывода, конкуренции и восстановления.

Каждый следующий PR должен иметь отдельный критерий готовности и результаты измерений. Расширять автономный цикл только на инструменты с проверенным учётом, понятным восстановлением и размеченными проверками качества. Флаги дают накопительную основу для анализа, но сами не являются генератором или валидатором всех идей.
